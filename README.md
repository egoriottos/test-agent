# test-agent

PoC AI-агента для разработки: получает путь к Java-файлу и имя метода, сам решает —
дописать новый тест-метод, актуализировать устаревший или создать тестовый класс с
нуля — и сразу пишет результат на диск, в тестовый файл рядом с исходным классом.

Та же архитектура, что и в `confluence-doc-agent`: компактно, слоями, без DTO на
каждую мелочь. Отличие от doc-агента — здесь модель не ограничена одним forced
tool-вызовом: это настоящий agentic tool use, где модель сама решает, какие ещё
файлы проекта ей нужно увидеть, прежде чем ответить.

```
TestAgentApplication.java     — точка входа, только main()
TestGeneratorController.java  — POST /generate-test
TestGeneratorService.java     — весь agentic loop + поиск класса по проекту + запись файла на диск
AnthropicClient.java          — вызов Anthropic Messages API (agentic tool use loop)
```

## Как это работает (agentic loop)

```
POST /generate-test  {"sourceFilePath": "...", "methodName": "..."}

1. observe — читаем исходный класс с диска; путь к тестовому классу вычисляем сами
             по конвенции (src/main/java/.../Foo.java -> src/test/java/.../FooTest.java)
             и читаем его, если он уже есть
2. decide  — просим Claude решить: ADD_TEST_METHOD / UPDATE_TEST_METHOD /
             CREATE_TEST_CLASS / NO_CHANGE. Модель не обязана отвечать сразу: у неё
             есть инструмент read_class_source(className), и она может вызвать его
             сколько угодно раз подряд — попросить исходник зависимости (чтобы точно
             замокать её) или соседний тестовый класс (чтобы перенять стиль команды).
             Наш код на каждый такой запрос просто ищет файл <className>.java в
             дереве проекта и отдаёт содержимое обратно. Только когда модель решит,
             что контекста достаточно, она вызывает submit_test_plan с готовым кодом
3. act     — сами (без LLM) вставляем/заменяем метод в файле или создаём новый файл;
             путь и то, ЧТО именно менять, решает не модель, а наш код
```

Раньше (v1) агент видел только один переданный файл и был вынужден отвечать одним
принудительным tool-вызовом сразу. Разница с этой версией — как раз ответ на вопрос
"а почему бы не дать ИИ доступ ко всему проекту": доступ есть, но не как "вывалить
всё в промпт", а как инструмент, которым модель пользуется по своей инициативе,
столько раз, сколько ей реально нужно (ограничено `MAX_TOOL_ITERATIONS = 6` — просто
защита от зацикливания, а не жёсткий бюджет "используй ровно N раз").

Решение "куда писать" и "какой кусок файла трогать" по-прежнему детерминированное:
путь к тестовому файлу вычисляется конвенцией в коде, а для UPDATE модель обязана
назвать точное имя старого метода (`existingTestMethodName`), который наш код находит
подсчётом фигурных скобок и заменяет целиком — остальные тест-методы не трогаются.

## Настройка

```bash
export ANTHROPIC_API_KEY="sk-ant-..."
```

## Запуск

```bash
gradle bootRun
```

Порт — 8081 (специально другой, чтобы можно было держать поднятым одновременно с
`confluence-doc-agent`, у которого 8080).

Через IntelliJ IDEA — как и раньше: открыть как Gradle-проект, прописать
`ANTHROPIC_API_KEY` в Run Configuration → Environment variables, запустить
`TestAgentApplication.main`. **Важно**: и `sourceFilePath`, и поиск классов через
`read_class_source` идут от рабочей директории процесса — если запускаешь из IDEA,
working directory по умолчанию и есть корень проекта (`test-agent/`), так что пути
вида `demo-project/src/main/java/...` в примерах ниже сработают как есть. Если
захочешь направить агента на свой реальный мегабилд — запускай его с рабочей
директорией в корне того чекаута (или поменяй `Path.of(".")` в
`findClassSource()`/`generateTest()` на нужный путь).

## Пример

В `demo-project/` — фиктивный мини-проект специально с цепочкой зависимостей
(`OrderController` → `OrderService` → `OrderRepository`), чтобы agentic tool use было
на чём показать:

- `OrderService.calculateTotal` — тест уже корректный → ожидаем `NO_CHANGE`
- `OrderService.applyDiscount` — тест есть, но устарел (скидка была 10%, стала 15%) →
  ожидаем `UPDATE_TEST_METHOD`
- `OrderService.cancelOrder` — метод без зависимостей, теста ещё нет →
  ожидаем `ADD_TEST_METHOD`, read_class_source агенту скорее всего не понадобится
- `OrderService.refundOrder` — методу нужен мок `OrderRepository` → ожидаем
  `ADD_TEST_METHOD`, и по дороге агент должен сам запросить `read_class_source("OrderRepository")`,
  чтобы увидеть сигнатуру `findAmount(String)`
- `OrderController.getRefundAmount` — тестового класса для контроллера нет вообще →
  ожидаем `CREATE_TEST_CLASS`; чтобы замокать `OrderService`, агенту нужен
  `read_class_source("OrderService")` (а через него, если захочет — ещё и
  `OrderRepository`); заодно в том же пакете лежит `OrderServiceTest.java`, где
  зависимость стабится лямбдой без Mockito — интересно посмотреть, подхватит ли
  модель этот стиль, если сама решит на него взглянуть
- `PaymentService.processPayment` — тестового класса нет, но и зависимостей у класса
  нет → контраст с предыдущим: read_class_source здесь агенту, скорее всего, не
  понадобится вообще

Все шесть запросов — в `samples/requests.http` (открой в IntelliJ IDEA и жми на
зелёные треугольники), либо curl, например:

```bash
curl -X POST http://localhost:8081/generate-test \
  -H "Content-Type: application/json" \
  -d '{"sourceFilePath": "demo-project/src/main/java/ru/bublikov/demo/OrderService.java", "methodName": "refundOrder"}'
```

После каждого запроса открой соответствующий файл в
`demo-project/src/test/java/ru/bublikov/demo/` — увидишь результат прямо там.
Чтобы посмотреть, сколько раз агент реально запрашивал файлы и что именно —
смотри лог приложения (уровень DEBUG уже включён в `application.yml`) или добавь
`System.out.println` в `AnthropicClient.decide()` перед разбором `tool_use`-блоков.

Чтобы попробовать на своём реальном коде — укажи `sourceFilePath` до настоящего
класса (относительный от рабочей директории агента, либо абсолютный) и запускай
агента с working directory, из которой достижимы нужные модули мегабилда.

## Автоматизация: тесты сами добавляются в коммит (git pre-commit хук)

Сценарий "создал ветку от main, написал сервис, закоммитил — а тесты уже в коммите"
— это не GitHub Actions (тот реагирует только после пуша и не может дописать файл в
уже сделанный локальный коммит), а обычный git pre-commit хук: срабатывает у тебя на
машине в момент `git commit`, до того как коммит зафиксирован, и может дозаписать
сгенерированный тест прямо в него.

В `git-hook/` — готовый хук:
- `pre-commit` — берёт список закоммиченных `.java`-файлов под `src/main/java`,
  для каждого достаёт список публичных методов и просит test-agent сгенерировать/
  актуализировать тест на каждый. Точным диффом "что именно изменилось" не
  занимается — просто прогоняет через агента все публичные методы файла, а
  решение ADD/UPDATE/NO_CHANGE агент и так принимает сам (см. выше). Если тест
  реально появился/изменился — дозаписывает его в текущий коммит (`git add`).
  Если test-agent не поднят — не блокирует коммит, просто предупреждает в консоли.
- `extract_public_methods.py` — вытаскивает имена публичных методов из файла
  регэкспом (без AST), нужен python3 на машине.

**Установка в твой реальный репозиторий** (не в `test-agent`, а в тот, где ты
пишешь сервисы):

```bash
mkdir -p .githooks
cp /путь/до/test-agent/git-hook/pre-commit .githooks/
cp /путь/до/test-agent/git-hook/extract_public_methods.py .githooks/
chmod +x .githooks/pre-commit
git config core.hooksPath .githooks
```

`git config core.hooksPath` — это стандартный способ держать хуки версионируемыми
(в отличие от `.git/hooks/`, который не коммитится и слетает при новом клоне) —
можно закоммитить `.githooks/` в репозиторий, и у всей команды хук будет работать
после одной команды `git config`.

**Важно**: сам `test-agent` в этот момент должен быть запущен с рабочей директорией
в корне ИМЕННО ТОГО репозитория, где ты коммитишь (не в `test-agent/`) — иначе пути
`sourceFilePath`/`testFilePath`, которые видит агент, не совпадут с тем, что видит
git в этом репозитории, и `git add` в хуке ничего не найдёт.

## Известные упрощения (осознанно, чтобы не разрастаться)

- Путь к тестовому классу вычисляется по одной жёсткой конвенции
  (`src/main/java` → `src/test/java`, `Foo.java` → `FooTest.java`). Если в реальном
  проекте тесты называются иначе (`FooTests`, лежат в другом модуле по другой схеме) —
  конвенцию нужно будет поправить под себя в `deriveTestPath()`.
- `read_class_source` ищет файл по простому имени класса (`findFirst()` по всему
  дереву от рабочей директории) — если в проекте есть два класса с одинаковым именем
  в разных пакетах, найдётся первый попавшийся, не обязательно тот, который имелся в
  виду. Для одного мегабилда с уникальными именами классов это обычно не проблема,
  но это не настоящее разрешение по FQN.
- Поиск и замена существующего метода — построчный подсчёт фигурных скобок по
  сигнатуре вида `void <имя>(...)`. Работает для обычных JUnit-тестов (они и так
  почти всегда `void`), но не рассчитан на экзотическое форматирование (сигнатура,
  размазанная на несколько строк с комментариями внутри скобок, и т.п.).
- Нет верхнего предела на то, СКОЛЬКО раз агент попросит файлы за один запрос, кроме
  общего `MAX_TOOL_ITERATIONS = 6` — для одного метода этого с запасом хватает, но
  для очень запутанного графа зависимостей теоретически можно упереться в лимит и
  получить `IllegalStateException` вместо ответа.
- Сгенерированные тесты не запускаются агентом — только записываются на диск,
  корректность (и то, что мок действительно матчится с реальным API зависимости)
  проверяет разработчик сам.
- `extract_public_methods.py` — регэксп, не AST-парсер. Не справится с сигнатурой,
  размазанной на несколько строк, дженериками с вложенными скобками
  (`Map<String, List<Foo>>`) или методами по интерфейсу без реализации в том же
  файле. Для типичного плоского сервисного класса работает нормально.
- Хук прогоняет ВСЕ публичные методы изменённого файла через агента при каждом
  коммите (не только реально изменившиеся) — при большом сервисе это может быть
  несколько секунд на коммит и несколько вызовов Anthropic API. Для PoC-масштаба
  это ок, для сотен методов в файле стоит доработать до реального диффа по методам.
